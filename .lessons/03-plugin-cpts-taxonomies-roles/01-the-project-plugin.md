# Lesson 03.1 — The Project Plugin

## Quick Overview

`blame-the-tech-core` is the plugin that owns every server-side registration in this course:
post types, taxonomies, statuses, roles, ACF field-group loading, GraphQL enums, custom
mutations, the leads table, the revalidation webhook. One plugin, one directory, one bootstrap
file, and a set of small files under `includes/` that later lessons add to. This lesson builds
the shell — the plugin header, a guard against direct access, the bootstrap that requires each
`includes/` file, and activation and deactivation hooks that are correct rather than merely
present.

It also introduces **Composer** and PSR-4 autoloading, which most Classic WordPress work never
touches. You will not `composer require` a framework; the dependency list stays empty for now.
What you want is the autoloader, so that classes you add in Modules 04, 06 and 18 —
`Blame\Core\Revalidate`, `Blame\Core\Leads` — load on demand instead of being manually
`require`d. Procedural files stay procedural where that is the clearer choice, which is
deliberate: this lesson makes an opinionated split rather than pretending object orientation is
free.

By the end of this lesson you will have:

- `blame-the-tech-core/blame-the-tech-core.php` — the plugin header, an `ABSPATH` guard, and a
  bootstrap that loads `includes/`
- `blame-the-tech-core/composer.json` with a PSR-4 map from `Blame\Core\` to `includes/`
- `vendor/autoload.php` generated by `composer install`, and `vendor/` confirmed gitignored
- `register_activation_hook` and `register_deactivation_hook` wired, doing only work that is
  safe to repeat
- The plugin active and listed by `wp plugin list`, with no notices in
  `docker compose logs wordpress`
- A written rule for what goes in the plugin versus the theme, in your own words

## Classic WP Analogy

You have written this file before, probably dozens of times: the `/** Plugin Name: ... */`
header, `defined('ABSPATH') || exit;`, a few `add_action` calls, maybe a class with a singleton
`get_instance()`. Nothing about the plugin API changes in a headless build. Hooks are hooks,
`plugins_loaded` still fires when it always did, and `register_activation_hook` still runs once
on activation and never again.

The real content of this lesson is the argument against the habit you almost certainly have.
In Classic WordPress, `functions.php` is where a small thing goes, and then a second small
thing, and eventually a 900-line file that registers three post types. That works because in
Classic WordPress the theme and the site are the same project. Here they are not: the theme is
a redirect stub, the front end is a separate application, and the server side must survive a
theme switch, be unit-testable in isolation (Module 23), and ship inside a production image
(Module 24). A registration in `functions.php` fails all three. Composer is the second habit
change — WordPress core has no autoloader, so if you want one you bring it, and PSR-4 is the
convention every other PHP project in the world already uses.

**Where the analogy breaks down:** activation hooks. In Classic WordPress an activation hook
that flushes rewrite rules or seeds terms is a one-time convenience, and if it misfires you
click Deactivate and Activate again. In this architecture the plugin is activated by a
`release_command` on every deploy to Fly.io, in a container, with no human watching and no
opportunity to click anything. So "runs once on activation" quietly becomes "runs on every
release", and anything in that hook must be idempotent — seeding a term must be
`term_exists()`-guarded, `dbDelta()` must be safe to re-run, and nothing may assume it is the
first time. Lesson 04.5 builds a versioned migration runner for exactly the cases where
idempotence is not achievable.

## Key Concepts

### 1. Four questions that decide plugin versus theme

The habit is `functions.php`. The argument against it is not style, it is four concrete
properties this project needs and a theme cannot provide.

| Question | `functions.php` | `blame-the-tech-core` plugin | `mu-plugins/` |
|---|---|---|---|
| Survives switching the theme? | ❌ every registration disappears | ✅ | ✅ |
| Can be deactivated to isolate a bug? | ❌ only by switching theme | ✅ `wp plugin deactivate` | ❌ always on |
| Loadable by a PHPUnit bootstrap without a theme? | ❌ needs `WP_Query` and a template | ✅ Module 23 loads it directly | ✅ |
| Version-controlled as its own unit, with its own `composer.json`? | ❌ shares the theme's | ✅ | ✅ |
| Right for | template helpers, `wp_enqueue_style` | **post types, taxonomies, roles, statuses, API surface** | environment hardening that must run before plugins |

**The verdict: everything server-side in this course is a plugin.** The `btt-headless` theme
from Lesson 02.4 keeps exactly one job — redirect front-end hits to Next — and never grows a
second one. Module 24 adds one `mu-plugin`, `000-btt-hardening.php`, because it has to run
before any plugin loads; that is the only exception in the whole course, and it earns it.

> **Where this breaks down:** a plugin can be deactivated, and a deactivated plugin means the
> `incident` post type does not exist, which means 40 rows in `wp_posts` become invisible to
> every query, `wp-admin` menu and GraphQL field. Content survives; access to it does not. That
> is the price of the isolation you just bought, and it is why Module 24's `release_command`
> activates plugins explicitly rather than trusting the database.

### 2. The plugin header is parsed, not decorative

WordPress reads the **first 8 KB** of every top-level `.php` file in a plugin directory looking
for a header block. The file that has one becomes the plugin's main file — the path
`wp plugin activate` takes, the path `plugin_basename()` returns, and the path
`register_activation_hook()` must be given.

| Header field | Parsed by WP | Why you care here |
|---|---|---|
| `Plugin Name` | yes — required | The only field that makes the directory a plugin at all |
| `Version` | yes | Compared by the updater; also what you read back in the migration runner in Lesson 04.5 |
| `Requires at least` | yes | WordPress **refuses activation** below this version |
| `Requires PHP` | yes | Same — refuses activation. This is your guard against a container built on the wrong PHP |
| `Text Domain` / `Domain Path` | yes | Module 20 loads translations from here |
| `License`, `Description`, `Author` | metadata | Shown in the plugins list; the licence matters because this plugin ships inside a distributed image |

`Requires PHP: 8.1` is not aspirational — it is a hard gate, and the cheapest possible defence
against a deploy landing on an older PHP and failing in a way that looks like a WordPress bug.

### 3. The load order you are hooking into

Everything in this module registers on `init`. Everything the plugin *is* — its constants, its
autoloader, its `require` chain — happens earlier, at file-load time.

```
                        one WordPress request
  ─────────────────────────────────────────────────────────────────────────────
  wp-config.php
      │
      ├─▶ mu-plugins load                         ← M24 hardening lives here
      │      muplugins_loaded
      │
      ├─▶ active plugins load, alphabetically     ← blame-the-tech-core.php RUNS
      │      · plugin header already parsed         · constants defined
      │      · vendor/autoload.php required         · Plugin::boot() requires includes/
      │      · add_action() calls registered        · NOTHING is registered yet
      │      plugins_loaded
      │
      ├─▶ theme functions.php
      │      after_setup_theme
      │
      ├─▶ init  ◀── register_post_type, register_taxonomy, register_post_meta,
      │             register_post_status, add_role  ALL fire here
      │
      ├─▶ wp_loaded
      └─▶ the query, then the response
```

Two rules fall out of that diagram and they are worth memorising:

1. **`add_action( 'init', ... )` at file-load time; `register_*()` inside the callback.** Calling
   `register_post_type()` directly at load time appears to work and then breaks in ways that are
   hard to attribute — `$wp_rewrite` is not ready, taxonomies attach to nothing, and other
   plugins that filter your arguments never get the chance.
2. **The plugin's own `init` callbacks did not run during its own activation.** The plugin was
   not active when `init` fired on that request. Key Concept 5 is entirely about the consequences.

### 4. Composer and PSR-4 in a codebase with no autoloader

WordPress core has no autoloader — every core class is `require`d by a file that names it, which
is why the ecosystem is full of long `includes/class-thing.php` chains. Composer solves it:
PSR-4 maps a namespace prefix onto a directory, and PHP calls the generated autoloader on first
use of an unknown class.

```
composer.json                        includes/
  autoload.psr-4                     ├── Plugin.php          → Blame\Core\Plugin
    "Blame\\Core\\": "includes/"     ├── Revalidate.php      → Blame\Core\Revalidate   (M18)
                                     ├── Leads.php           → Blame\Core\Leads        (M16)
                                     ├── post-types.php      ─┐
                                     ├── taxonomies.php       │ procedural — required
                                     ├── roles.php            │ explicitly by Plugin::boot()
                                     └── statuses.php        ─┘
```

The split is deliberate, and this course takes a position on it:

| | Autoloaded class | Explicitly required procedural file |
|---|---|---|
| File name | `StudlyCase.php`, matching the class | `kebab-case.php` |
| Loaded | on first use of the class | on every request, by `Plugin::boot()` |
| Good for | anything with state or collaborators — a webhook signer, a leads repository | a flat list of `add_action` calls |
| Bad for | six `add_action` calls wrapped in a class for no reason | anything you want to unit test in isolation |

**The rule: if wrapping it in a class would not let you test it or reuse it, do not wrap it in a
class.** Module 23 tests `includes/post-types.php` by firing `init` and asserting on
`get_post_type_object()`, which is a better test than asserting that a method was called.

> **Composer is not in the WordPress image, and neither is WP-CLI.** The stock
> `wordpress:6.8-php8.3-apache` image ships neither binary. WP-CLI comes from the `wpcli`
> service you already have; Composer gets a service of its own in Step 5. Because the plugin
> directory is a bind mount, the `vendor/` tree Composer writes on your disk is immediately
> visible inside the `wordpress` container, which does have PHP. See
> [appendix 07 §2](../appendix/07-command-reference.md) for the invocation you will type a
> hundred times.

`vendor/` is gitignored (root `.gitignore`, `vendor/`); `composer.json` **and** `composer.lock`
are committed. The lock file is what makes `composer install` reproducible — Module 24's image
build runs `composer install --no-dev --optimize-autoloader --no-interaction`, and without a
lock file that command resolves versions afresh at build time, which is how two builds of the
same commit end up different.

### 5. Activation, deactivation and uninstall are three different lifecycles

Most plugins treat these as one concept with three names. They are not.

| | `register_activation_hook` | `register_deactivation_hook` | `uninstall.php` |
|---|---|---|---|
| Fires when | the plugin is activated | the plugin is deactivated | the plugin is **deleted** |
| Plugin code loaded? | yes, this request | yes, this request | **no** — nothing but WordPress |
| Did the plugin's `init` run this request? | **no** | yes | n/a |
| Runs on every deploy? | **yes** — the Fly.io `release_command` activates plugins | no | no |
| Belongs here | term seeding, `dbDelta()`, role creation, one rewrite flush | dropping caches you own | deleting your options and roles |
| Never belongs here | anything slow, anything network, anything non-idempotent | deleting data — deactivation is not deletion | deleting user content |

The "`init` did not run" row is the one that produces real bugs. WordPress activates a plugin
by including its main file and firing `activate_{$plugin}` — during an admin request in which
`init` had already fired *before* your plugin existed. So at activation time your post types
are **not registered**, your taxonomies are **not registered**, and this fails silently:

```php
// wordpress-headless/wp-content/plugins/blame-the-tech-core/includes/Plugin.php
// ❌ Wrong: there are no `incident` rewrite rules to flush yet, so this
//    writes a rule set that does not include your post type.
public static function activate(): void {
    flush_rewrite_rules();
}

// ✅ Right: register by hand first, then flush, then stop.
public static function activate(): void {
    register_post_types();   // the same function `init` will call on the next request
    register_taxonomies();
    seed_default_terms();
    flush_rewrite_rules();
}
```

The symptom of getting this wrong is the single most common WordPress support question there
is: the post type appears in wp-admin, editing works, and every permalink 404s until you visit
Settings → Permalinks and click Save. Clicking Save calls `flush_rewrite_rules()` at a moment
when the post type *is* registered, which is why it "fixes itself".

### 6. Why the rewrite flush belongs in the activation hook and nowhere else

Rewrite rules are an array of roughly a hundred regular expressions, serialised into a single
`wp_options` row called `rewrite_rules`. `flush_rewrite_rules()` walks every registered post
type, taxonomy and endpoint, rebuilds the whole set, and writes that row — around 20 KB of
serialised array. With `$hard = true` (the default) it also asks WordPress to rewrite
`.htaccess`.

| Where you call it | Cost | Correct? |
|---|---|---|
| `register_activation_hook` | once per activation | ✅ **this** |
| `init`, unconditionally | a `wp_options` write on **every request** | ❌ the classic performance bug |
| `init`, behind a version-option check | one write when the version changes | acceptable, and what Lesson 04.5's migration runner generalises |
| `admin_init` | a write on every admin request | ❌ same bug, less visible |

Deactivation is the mirror image and has a subtlety. During its own deactivation request the
plugin is **still loaded**, so `init` already registered your post types — calling
`flush_rewrite_rules()` there would helpfully rebuild the rule set *including* the rules you are
trying to retire. Deleting the option instead lets WordPress rebuild it on the next request from
whatever is actually registered then:

```php
// wordpress-headless/wp-content/plugins/blame-the-tech-core/includes/Plugin.php
delete_option( 'rewrite_rules' );   // soft flush: rebuild lazily, from reality
```

### 7. Idempotency, because activation is not a one-time event

In Classic WordPress "activation" is something a human does once. Here it is a line in Module
24's Fly.io `release_command`, which runs `wp core update-db`, then
`wp plugin activate blame-the-tech-core`, then `wp blame migrate`, then
`wp rewrite flush --hard`, on **every deploy**. So every statement in `activate()` must be safe
to run for the fifth time. Three patterns cover almost everything:

| Pattern | Use for | Function |
|---|---|---|
| Existence guard | terms, roles, pages | `term_exists()`, `get_role()`, `get_page_by_path()` |
| Declarative diff | database tables | `dbDelta()` — compares the schema you declare against what exists |
| Version gate | anything genuinely one-way | an option holding a version number; Lesson 04.5 builds the runner |

Note that `wp plugin activate` on an already-active plugin is a no-op and does **not** re-fire
the hook — so a deploy that changes nothing costs nothing. The hook fires when the state
actually transitions, which is exactly when you want it to, and is also exactly why a
version-gated migration runner is still necessary: activation cannot be your migration mechanism
because it will not run when you need it to.

### Step 1: Create the plugin skeleton

```bash
cd wordpress-headless/wp-content/plugins
mkdir -p blame-the-tech-core/includes

```

The directory name matters. `wp plugin activate blame-the-tech-core` takes the *directory*
name, and appendix 03 §8 fixes it. Nothing in this course refers to the plugin by any other
string.

### Step 2: Write the bootstrap file

This is the only file WordPress finds by itself. Everything else is reached from here.

```php
// wordpress-headless/wp-content/plugins/blame-the-tech-core/blame-the-tech-core.php
<?php
/**
 * Plugin Name:       Blame The Tech — Core
 * Description:       Post types, taxonomies, statuses, roles, ACF loading, GraphQL extensions and the `wp blame` CLI.
 * Version:           0.1.0
 * Requires at least: 6.5
 * Requires PHP:      8.1
 * Author:            Blame The Tech
 * License:           GPL-2.0-or-later
 * License URI:       https://www.gnu.org/licenses/gpl-2.0.html
 * Text Domain:       blame-the-tech-core
 * Domain Path:       /languages
 *
 * @package Blame\Core
 */

declare( strict_types=1 );

namespace Blame\Core;

// Direct access to a PHP file inside wp-content must not execute anything.
defined( 'ABSPATH' ) || exit;

const VERSION     = '0.1.0';
const PLUGIN_FILE = __FILE__;
const PLUGIN_DIR  = __DIR__;

$btt_autoload = __DIR__ . '/vendor/autoload.php';

// vendor/ is gitignored, so a fresh clone has no autoloader until someone runs
// `composer install`. Fail with a sentence that says what to type, not a fatal.
if ( ! is_readable( $btt_autoload ) ) {
	add_action(
		'admin_notices',
		static function (): void {
			printf(
				'<div class="notice notice-error"><p><strong>%s</strong> %s</p></div>',
				esc_html__( 'Blame The Tech Core is not loaded.', 'blame-the-tech-core' ),
				esc_html__(
					'vendor/autoload.php is missing. Run: docker compose run --rm composer install',
					'blame-the-tech-core'
				)
			);
		}
	);

	return;
}

require_once $btt_autoload;

Plugin::boot();

// These take the MAIN plugin file. Passing __FILE__ from inside includes/ is a
// classic and silent mistake: the hook name would not match and nothing fires.
register_activation_hook( PLUGIN_FILE, array( Plugin::class, 'activate' ) );
register_deactivation_hook( PLUGIN_FILE, array( Plugin::class, 'deactivate' ) );
```

`declare( strict_types=1 )` has to be the first *statement* in the file — a docblock above it is
fine, a `namespace` above it is a fatal error. Strict types means the string `"90"` arriving
where an `int` is declared throws a `TypeError` instead of quietly becoming `90`, which is what
you want in a codebase whose input comes over HTTP.

### Step 3: Write the bootstrap class

This is the first autoloaded class, so it is also the proof that the autoloader works.

```php
// wordpress-headless/wp-content/plugins/blame-the-tech-core/includes/Plugin.php
<?php
/**
 * Plugin bootstrap and lifecycle.
 *
 * @package Blame\Core
 */

declare( strict_types=1 );

namespace Blame\Core;

defined( 'ABSPATH' ) || exit;

/**
 * Loads every registration file and owns the three lifecycle hooks.
 *
 * Deliberately not a singleton. There is no instance state to protect, so
 * `get_instance()` would be ceremony. Static methods are honest about that.
 */
final class Plugin {

	/**
	 * Procedural registration files, required on every request in this order.
	 *
	 * Each later lesson in Modules 03 and 04 adds exactly one line here.
	 *
	 * @var string[]
	 */
	private const INCLUDES = array(
		// 'includes/post-types.php',   ← Lesson 03.2
		// 'includes/taxonomies.php',   ← Lesson 03.3
		// 'includes/statuses.php',     ← Lesson 03.4
		// 'includes/roles.php',        ← Lesson 03.5
	);

	/**
	 * Files loaded only under WP-CLI. Lesson 04.4 fills this in.
	 *
	 * @var string[]
	 */
	private const CLI_INCLUDES = array();

	/**
	 * Wire the plugin up. Called at plugin-load time, before `init`.
	 */
	public static function boot(): void {
		foreach ( self::INCLUDES as $file ) {
			require_once PLUGIN_DIR . '/' . $file;
		}

		if ( defined( 'WP_CLI' ) && WP_CLI ) {
			foreach ( self::CLI_INCLUDES as $file ) {
				require_once PLUGIN_DIR . '/' . $file;
			}
		}
	}

	/**
	 * Runs on activation — which, in this project, means on every deploy.
	 *
	 * `init` has NOT fired for this plugin in this request, so anything that
	 * depends on a registration has to trigger that registration itself.
	 * Every statement here must be safe to run again.
	 */
	public static function activate(): void {
		// Later lessons add their calls here, above the flush:
		//   03.2  register_post_types();
		//   03.3  register_taxonomies();  seed_default_terms();
		//   03.5  register_reporter_role();

		// LAST. Everything that adds a rewrite rule must already have run.
		flush_rewrite_rules();

		// autoload = false: this is read by the migration runner, not on the
		// request path. Lesson 02.3 explains why that third argument matters.
		update_option( 'btt_core_version', VERSION, false );
	}

	/**
	 * Runs on deactivation. Deactivation is not deletion — remove nothing a
	 * user would miss.
	 */
	public static function deactivate(): void {
		// Soft flush. The plugin is still loaded right now, so
		// flush_rewrite_rules() would rebuild the rule set *including* our own
		// rules. Deleting the option lets WordPress rebuild it on the next
		// request from whatever is actually registered then.
		delete_option( 'rewrite_rules' );
	}
}
```

**Verify §3:**

- [ ] The file is `includes/Plugin.php` — capital `P`, matching the class name. PSR-4 is
      case-sensitive, and a lowercase `plugin.php` autoloads on macOS and fails in the Linux
      container. This is the single most common PSR-4 bug.
- [ ] The namespace is `Blame\Core`, with no trailing `\`.

### Step 4: Write `composer.json`

No dependencies yet. You are here for the autoloader.

```json
{
  "name": "blame-the-tech/core",
  "description": "Server-side content model and API surface for Blame The Tech.",
  "type": "wordpress-plugin",
  "license": "GPL-2.0-or-later",
  "require": {
    "php": ">=8.1"
  },
  "autoload": {
    "psr-4": {
      "Blame\\Core\\": "includes/"
    }
  },
  "config": {
    "optimize-autoloader": true,
    "sort-packages": true,
    "platform": {
      "php": "8.3"
    }
  }
}
```

That file goes at `wordpress-headless/wp-content/plugins/blame-the-tech-core/composer.json`.
Three keys are doing real work. `"Blame\\Core\\": "includes/"` — the double backslash is JSON
escaping, not a typo; in PHP the prefix is `Blame\Core\`. `platform.php: "8.3"` pins what
Composer *resolves against* to the container's PHP, so it cannot pick a package the image
cannot run. And `require.php: ">=8.1"` matches the `Requires PHP` header — two places
deliberately, because WordPress reads the header and Composer reads this.

### Step 5: Add a `composer` service to the stack

The plugin directory is already bind-mounted, so a container that writes `vendor/` writes it
onto your disk, where both your editor and the `wordpress` container can see it. Add this
service to `docker-compose.yml`, alongside `wpcli`:

```yaml
# wordpress-headless/docker-compose.yml (fragment — add under `services:`)
  composer:
    # Pinned to a Composer MINOR, not to `composer:2`, so a resolver change
    # cannot land on you mid-course. There is deliberately no PHP in this tag:
    # the official image publishes no `-phpX.Y` variants, and `composer:2.9`
    # currently runs PHP 8.5 even though this plugin targets 8.3. That is why
    # `config.platform.php` in Step 4's composer.json is not optional — it is
    # what makes RESOLUTION target 8.3. Anything Module 23 EXECUTES here still
    # executes on the image's PHP, which is newer than production's.
    image: composer:2.9
    # Run-on-demand, same as wpcli: without a profile, `up` starts this container,
    # its default command (Composer's own help listing) exits, and `up -d --wait`
    # returns 1. `docker compose run` activates the profile for you.
    profiles: ['cli']
    working_dir: /app
    volumes:
      - ./wp-content/plugins/blame-the-tech-core:/app
    environment:
      # Without this, Composer warns about an unwritable home directory.
      COMPOSER_HOME: /tmp/composer
      COMPOSER_ALLOW_SUPERUSER: 1
    # Write vendor/ as you, not as root. On Docker Desktop this is cosmetic; on
    # Linux, a root-owned vendor/ on a bind mount is genuinely annoying to delete.
    user: '${UID:-1000}:${GID:-1000}'
    networks: [btt-net]
```

Those two variables need a value, and the obvious way to supply one does not work. `UID` and
`GID` are shell variables rather than environment variables, so Compose cannot see them — but in
**bash**, the default shell on essentially every Linux distribution, `GID` does not exist at all
and `UID` is read-only, so `export UID GID` gets you `501:1000` with a silently wrong group and
`UID=$(id -u)` gets you `bash: UID: readonly variable`. Put them in your gitignored `.env`
instead, where Compose reads them the same way it reads `COMPOSE_FILE`:

```dotenv
# wordpress-headless/.env  (append — machine-local, never committed)
# Ownership for vendor/ written by the `composer` service. Yours will differ:
# run `id -u` and `id -g` and paste the two numbers.
UID=501
GID=20
```

Unset, they default to `1000:1000`, which is right on a single-user Linux box and cosmetic on
Docker Desktop.

### Step 7: Write `uninstall.php`

Deletion is the third lifecycle, and it runs in a request where **none of your code is
loaded** — no autoloader, no namespace, no constants. Everything it needs, it does itself.

```php
// wordpress-headless/wp-content/plugins/blame-the-tech-core/uninstall.php
<?php
/**
 * Runs when the plugin is DELETED from the plugins screen or by
 * `wp plugin delete`. Never on deactivation.
 *
 * WordPress loads this file in isolation with WP_UNINSTALL_PLUGIN defined and
 * no plugin code loaded, so it can use core functions and nothing else.
 *
 * @package Blame\Core
 */

declare( strict_types=1 );

// Without this guard the file is directly requestable over HTTP.
defined( 'WP_UNINSTALL_PLUGIN' ) || exit;

// Our own bookkeeping. Safe to delete.
delete_option( 'btt_core_version' );
delete_option( 'btt_db_version' );

// Rules that mention post types nothing will register any more.
delete_option( 'rewrite_rules' );

// Lesson 03.5 adds `remove_role( 'incident_reporter' );` here.

/*
 * Deliberately NOT deleted: posts, terms, post meta, uploads, wp_btt_leads.
 * The content is the user's, not the plugin's. A destructive teardown belongs
 * behind an explicit `wp blame reset` (Module 12), typed by a human.
 */
```
